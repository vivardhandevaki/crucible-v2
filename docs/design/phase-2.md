## §1 Archive & the regression suite

- `crucible archive <change>`: shells out to `openspec archive <change> --yes` *(resolved P2-00 from the spike: the whole change dir — Crucible-owned `approval.yaml`/`state.yaml` included — moves intact to `openspec/changes/archive/YYYY-MM-DD-<name>/`, and deltas merge into `openspec/specs/<capability>/spec.md` with `[REQ-*]` bracketed headings preserved)*. Preconditions, fail-closed: bundle passes Crucible's own parsers, seal valid, and `openspec validate --strict --json` reports `valid` — **parse the JSON verdict, never the exit code** (spike D4). Archiving thereby registers the change's bindings in the regression set.
- Regression collection: scan `openspec/changes/archive/*/oracles.md` (the date prefix is OpenSpec-owned and opaque to collection) with the P1-03 oracle parser → union of bindings, grouped by runner. No separate registry (charter: archiving is registration).
- Lint upgrade: `requirement:` may now reference archived REQ IDs (bugfix/ratchet oracles). Archived-REQ index built from `openspec/specs/**/spec.md` bracketed headings (spike-verified to survive the merge) + archived deltas. *(As-built P2-01:)* the index is a pure filesystem read (`regression/regression.ts` `collectArchivedRequirementIds`) threaded into `lintTraceability` as a 4th arg (default empty set, so P1-era callers are unchanged); it relaxes ONLY the orphan check — an oracle's `requirement:` is legal if it is in the delta **or** the archived index; coverage is unchanged (still delta-only). Wired into verify, approve, and the propose/amend bundle judge alike, so a bugfix oracle binding an old REQ passes at every stage.
- *(As-built P2-01 — archive command:)* the deterministic core (`commands/archive.ts`) injects the two OpenSpec edges (`validate`, `archive`); its preconditions run in a fixed fail-closed order — bundle exists (exit 2) → **approved** (exit 2; an unsealed change has no sealed bindings to register) → Crucible parsers (exit 3) → seal still valid (exit 2) → `openspec validate` valid (exit 3) — all *before* the irreversible move, which the core then confirms landed (source dir gone + an `archive/*-<name>` entry appeared) rather than trusting the archiver's silence (invariant 3). The audit event is appended into the MOVED `state.yaml` best-effort (the archive is done; a derived-log write must not fail it — invariant 1).
- *(As-built P2-01 — verify regression run:)* verify re-runs the whole regression suite alongside the current change's oracles (one injected `run` batch, results partitioned by id) and reports it as a **distinct `regression` check** (added to `CHECK_NAMES`) so a broken PAST promise reads differently from a failing current oracle. The suite is collected fresh from disk each run (`collectRegressionSuite`); an empty archive emits no `regression` check. Both runs sit behind the same lint gate (a red current lint short-circuits both — the cheap gate stays first).

## §2 Tier computation & routing

- `tier/` implements the charter table: inputs = spec-delta presence, risk-glob matches (enforcement config), diff size. `tier/` itself is **pure** — facts in, decision out, no I/O (invariant 12); the git edge that assembles diff facts is injected by the caller, following the P1-14 `StatusDeps.readMergeBaseConfig` precedent. *(Resolved P2-00 — diff acquisition:)* `verify` gains `--diff-base <ref>`; the CI template passes `origin/<base_ref>` (the shipped workflow already checks out with `fetch-depth: 0`, so the diff is computable); locally the default base is the merge-base of HEAD and `origin/HEAD`. In enforcement contexts (verify, CI) an uncomputable diff is exit 3 — never "assume trivial"; `status` remains best-effort (convenience, P1-14 rule). Output includes the *facts* used (for state.yaml and `status` display).
- Recomputation points: propose (suggest), approve (display + record), implement (refuse on mismatch with claim), CI verify (authoritative).
- Routing: verify's report gains `routing: auto | human` + reasons. Mechanically *(resolved P2-00)*: the shipped workflow gains a second **required job `route`** (`needs: verify`) in the same `crucible.yml`, consuming the routing decision from verify's `--json` report via job output. When routing is `human`, `route` queries the PR's reviews through the ambient `GITHUB_TOKEN` (`permissions: pull-requests: read`) and stays red until an APPROVED review from a non-author exists; the workflow adds a `pull_request_review` trigger so the check re-evaluates when the approval lands. Auto-merge is enabled per-repo via branch settings + GH auto-merge — Crucible emits the decision, GitHub enforces it. Trivial/standard green → auto-merge path; critical → required human review.
- Diff caps enforced in verify (per-tier from config); stacked-change plans deferred to just-in-time (backlog A6) unless the validation project needs them earlier.
- *(Resolved P2-18 — invariant #7's behavioral-anchor harness:)* a **hermetic test-repo** (vitest), not `act`. `core/test/target-branch-rule.test.ts` builds a real temp git repo (target branch carries the strict config + bundle; the PR branch touches a `src/**` file and loosens the glob), reproduces the shipped workflow's extraction command (`git show <target>:crucible.yaml` → a dir outside the PR tree), and runs the real `verify` core with the extracted config + real git diff facts — asserting the loosened-glob PR still routes **human** under the target config, **auto** under its own config, and auto once the loosening has merged to the target. The adapter is orthogonal to invariant #7 (the P1-16 tracer covers the real stub adapter), so oracle resolve/run are injected pass-throughs. **`act` was rejected:** the framework CI is pure Node/npm with no `act`/runner images, so it would either add heavy Docker infra or silently not gate most PRs, and the `route` job's reviews-API call still needs mocking — fidelity to the static YAML that the structural template test (`ci-templates/src/crucible-template.test.ts`) already provides. (The task line said "per P2-00-resolved harness," but P2-00 did not actually pin it; resolved here.)

## §3 amend / override / escalate

- **escalate:** writes `escalation.yaml {oracle?, question, options[], filed_at}`; ends implement run; implement precondition: refuse while unresolved. Notify hooks fire. *(As-built P2-04:)* the artifact carries `version`/`change`/`filed_by` alongside those fields for parity with the other strict, self-describing bundle artifacts (fail-closed at exit 3 like the rest). "Ends implement run" + "refuse while unresolved" are one shared exit-2 gate teaching `crucible amend`, checked both mid-run (after the implement session files one) and at the top of every resume. Notify is an injected `NotifyFn` edge (`core/src/notify/types.ts` — the contract P2-15's dispatcher fills); escalate fires it fire-and-forget and swallows any throw/rejection (invariant 11), so a broken hook never blocks the escalation. The CLI wires a no-op notify until P2-15 lands.
- **amend:** interactive resolution + general mid-flight spec fixes. Flow *(UX ratified P2-00 as charter-described)*: show approved-vs-current artifact diff (or escalation options) → human picks/edits → substrate(role=propose) regenerates affected artifacts + bound tests → human confirms that diff → append `amendments[]` entry to approval.yaml with fresh hashes (the P1-06 `amendments` array, present-but-unused until now) → clear escalation. Staleness rules from charter §Editing Artifacts apply pre-approval via `propose --revise` (also this phase; `--revise` reuses the same propose-role regeneration path). *(As-built P2-05:)* (a) the generation ledger is a committed **`generation.yaml`** in the change dir — `{version, change, generated_at, artifacts:[{path, hash}]}` in dependency order (proposal → design → specs → oracles), stamped by propose/`--revise`/amend on a green bundle and **excluded from the approval hash scope** (a pre-approval coherence guard, not the seal). A bundle with no ledger (P1-era / hand-authored) has no lineage to check and passes — the post-approval seal is the hard guarantee. Staleness = a hand-edit to any artifact *upstream of the leaf* (only a leaf/oracles edit is always safe). (b) the "confirm consistency" escape is `crucible approve --confirm-consistency`, which re-stamps the ledger to current bytes then seals. (c) the appended `amendments[]` entry is `{at, files}` (the fresh full map — charter's "delta entry with new hashes"); the live `approval.files` is updated in lockstep so `verifyApproval` stays unchanged, and who/why lives in the state event + notify. (d) a **red** regeneration re-seals nothing and clears no escalation (exit 1, the ambiguity stays unresolved); notify fires fire-and-forget (invariant 11).
- **override:** `crucible override "<reason>"` writes `override.yaml`; verify treats gate-bypass as permitted but marks the report `override: true`; CI forces human review regardless of tier and files the ratchet issue that stays open until a retroactive change references it. *(Resolved P2-00 — token plumbing:)* no token plumbing in core. Issue filing is a CI-template step using the ambient `GITHUB_TOKEN` (`permissions: issues: write`); core emits the issue payload inside the report JSON, the step files it idempotently (searches open `crucible-override`-labeled issues for the change before creating). Local runs never file issues — notify hooks may announce (convenience, invariant 11).

## §4 Change types

- Schema bundle gains `feature` / `bugfix` / `refactor` variants. *(Resolved P2-00 — mechanism, per spike:)* three **sibling bundles** — `crucible` (feature, the default), `crucible-bugfix`, `crucible-refactor` — shipped as plain files from a new root **`schemas/` workspace** (as-built finding: the workspace named in CLAUDE.md's repo layout does not exist yet; P2-07 creates it). Bundles are always installed by copying, never via OpenSpec's generator (spike: `schema init --artifacts` rejects unknown artifact IDs like `oracles`); `propose` passes `--schema` explicitly on `openspec new change` (spike D5: never rely on ambient default-schema resolution); the change's `.openspec.yaml` pins its schema thereafter. The change *type* is therefore the schema choice: recorded in `.openspec.yaml` + proposal frontmatter, revalidated by Crucible at approve/implement/CI exactly like tier claims (OpenSpec's ordering remains advisory — spike D3 — so all type enforcement is Crucible's own).
- `refactor`: spec delta present → exit 3 at propose; lint requires zero new oracles; correctness = regression suite.
- `bugfix`: requires ≥1 new oracle marked `reproduces: true`; verify gains the **red-on-base/green-on-fix** check: run the reproduction target against merge-base (worktree checkout) expecting fail, against head expecting pass. Fail-closed: reproduction passing on base → exit 1 ("does not reproduce").
- Type inference in propose from intent text; `--type` overrides; recorded in proposal frontmatter and re-validated like tiers.

*(As-built P2-07 — the change-type module + threading:)*
- **The record is the `.openspec.yaml` schema pin, not proposal frontmatter.** The scaffold writes `schema: <sibling bundle>` (Crucible-controlled), so the recorded type is a byte Crucible owns, not agent prose that could drift; `readChangeType` maps the pin back (unknown pin → exit 3). The type is also mirrored into `state.yaml`'s `snapshot.change_type` for `status` display (derived, invariant 1) — but `status`/`verify` re-read the pin, never the cache. (The original "proposal frontmatter" note is superseded: an agent-authored frontmatter field is exactly the kind of self-report invariant 2 says is worth zero.)
- **Conformance is one fail-closed gate (`assertTypeConformance`), applied at propose / approve / verify** — the type analogue of "tiers are computed, never declared." It throws exit 3 on: refactor with a spec delta, refactor with any oracle, bugfix with no `reproduces: true` oracle. The design's "refactor lint requires zero new oracles" is realized as this exit-3 conformance rule rather than a soft lint finding: both refactor violations are structural breaches of the pinned schema, and invariant 3 makes structural breaches fail closed (uniform with "spec delta present → exit 3"). At propose the gate runs only once the `bundle` check is green (artifacts parse), so a malformed artifact stays a red `bundle` finding (the propose judgment boundary) rather than being reclassified as exit 3; the refactor-with-spec-delta case still reaches exit 3 because its spec delta is the ROOT cause of any downstream coverage red.
- **Only `feature` requires a spec delta.** `loadRequirementsForType` returns `[]` for bugfix/refactor when `specs/` is absent (expected), and the `bundle` judge no longer flags a missing spec delta for those types. A refactor bundle keeps an EMPTY `oracles.md` (title only) so the hash scope, seal, and verify machinery stay uniform across types — the empty file is the sealed statement "this change adds no new oracles."
- **The `oracles.md` binding schema gains an optional `reproduces: boolean`** (P2-08 runs the red-on-base/green-on-fix check on the marked targets). P2-07 ships the bugfix bundle + the `reproduces` field + the "≥1 reproduction oracle" conformance rule; the merge-base worktree run itself is P2-08.
- **The three bundles live in the root `schemas/` workspace** (`crucible`, `crucible-bugfix`, `crucible-refactor`), validated by `changetype/schema-bundle.ts` (zod shape + templates exist + `requires` resolve + acyclic). `crucible init` (P2-12) copies them into a target repo's `openspec/schemas/`.

*(As-built P2-08 — the merge-base worktree run:)*
- **`reproduction/reproduction.ts` owns the red-on-base run; `verifyx/report.ts` owns the verdict.** verify's ordinary `oracles` check already proves GREEN-ON-FIX (the `reproduces: true` oracles run against HEAD like any other), so P2-08 only adds RED-ON-BASE: a new `reproduction` check that runs the same reproduction oracles against the merge-base and is green iff every one of them **fails** there. A reproduction that *passes* on base is the red — exit 1, "does not reproduce" (the design fixed the check; this is its verdict surface). A non-`pass` on base (fail/error/skip, the client already coerces the latter two to fail) is the correct outcome: a reproduction that cannot even run against the old source has still not passed.
- **Mechanism (the design fixed the check, not its plumbing):** `runReproductionOnBase` checks the merge-base out into a **throwaway git worktree** under `.crucible/worktrees/repro-<sha(base)>`, **overlays** the reproduction oracles' resolved test files from the working tree onto that old source (the charter's "the new test on the pre-fix commit" — new test, old source; only the test files move, so the fix's source stays at base), runs the adapter with `cwd` = the worktree, and **always** removes the worktree in a `finally` (cleanup proven even on throw — invariant 3). Overlay is a plain working-tree copy (not `git checkout`), so an as-yet-uncommitted reproduction test is still carried onto base during a local loop.
- **The run is an injected edge (`VerifyDeps.runOnBase`), gated exactly like tier.** It spawns git + the adapter, so it is supplied only on the authoritative CLI/CI path (alongside `diffFacts`); an inner-loop / pre-approve verify omits it and skips the reproduction check, just as it skips tier without `diffFacts`. The core stays deterministic (invariant 12): the git worktree lifecycle (`WorktreeGit`) and the adapter edges are all injected, so the check is hermetically testable and the real edge (`liveWorktreeGit`) is proven end-to-end against a real two-commit repo + the real stub adapter (`core/test/bugfix-flow.test.ts`). The check runs only for `type === 'bugfix'` and only when the traceability lint is green (a merge-base run against unresolved bindings is moot) — conformance already guarantees a bugfix carries ≥1 reproduction oracle, so the batch is never empty for a well-formed bundle. The live adapter edges stay `init`-pinned (P2-12) like the HEAD `run`/`resolve`; only the worktree plumbing is wired now.

## §5 Adversarial reviewer

- `.crucible/rubric.yaml` loader + zod schema (charter format). Rubric is TCB: included in approval hash scope? **No** — rubric is repo-global, protected by risk globs + target-branch rule, not per-change hashing. Verdicts pin `rubric_hash`.
- `commands/review.ts`: substrate(role=review, fresh context) with inputs = diff, spec delta, oracles, rubric. *(Resolved P2-00 — structured output:)* the frozen substrate result stays `{exitCode, transcriptPath}` and is never parsed for content (architecture §6, invariant 2). The review command **mints a verdict path** — `.crucible/verdicts/<change>/review-<ts>.json`, the same caller-minted-path rule as transcripts — names it in the taskPayload ("write your verdict JSON to exactly this path"), and core loads + zod-validates that file after the run. A missing file is just another malformed verdict.
- Fail-closed enforcement in core, not prompt: malformed → fail; fail-with-no-block-findings → fail; unknown rubric ID → fail. Observations attached to verify report + PR comment.
- `verify --review` optional locally; CI always. Reviewer model from settings.yaml `models.review` (prefer_different_family honored when resolvable).
- `.crucible/context/review.md` authored this phase (Fable-tier): instructs evidence-cited findings only, observations channel, no invented rules.

*(As-built P2-10 — the review command + verify threading:)*
- **The whole review flow sits behind one injected verify edge** (`VerifyDeps.review`, supplied under `--review`; the shipped CI workflow always passes the flag — "CI always" is a property of the template, not a CI-detection branch in core). The edge is gated on a green traceability lint exactly like the oracle run: a bundle that does not parse is already red, and no agent is spent reviewing it. The check name is `review`; the report gains optional `review` extras `{rubric_hash, model?, observations[]}` — `rubric_hash` is computed by CORE from `.crucible/rubric.yaml` and passed to the P2-09 evaluator as `expectedRubricHash` (the verdict must match it; the pin is never taken from the verdict), and `model` is the verdict's self-declared identity (the charter's v2.0-light drift guard — audit, not enforcement).
- **Finding render is the `why` trail** (P2-16's input): finding id = the rubric line, message = `explanation — file:line; fix: remediation`. A fail-closed outcome with no rubric line to cite (NO_VERDICT / MALFORMED_VERDICT / UNKNOWN_RUBRIC_ID / INCONSISTENT_VERDICT / RUBRIC_HASH_MISMATCH) uses the machine code as the finding id.
- **`prefer_different_family` is honored as default routing, not a config key:** with a single-provider substrate and no model-family metadata to resolve, the review default is `claude-haiku-4-5` — cheap and a different family than implement's `claude-opus-4-8` default (charter Learnings #2). An explicit `models.review` always wins; a `prefer_different_family` knob becomes meaningful only if a models registry ever lands (backlog).
- **PR observations output:** the verify step stashes `report.review.observations` BEFORE its red-verdict exit (a blocked change still surfaces its harvest), and a fail-closed `always()` step posts ONE marker-tagged comment (`<!-- crucible-observations -->`, `gh pr comment --edit-last --create-if-none` — edited in place on re-runs, no spam). Fail-closed like the override-issue step: the harvest channel is enforcement paper-trail, not a notify hook. The verify job takes job-level `pull-requests: write` for it; `route` keeps workflow-level `read`.
- **The review core writes no state** — review is an input to verify's read-only judgment; only the standalone `crucible review` CLI appends a state audit event, best-effort (invariants 1/11). Verdicts land at the caller-minted `.crucible/verdicts/<change>/review-<ts>.json` (gitignored at init, P2-12, like transcripts).

## §8 Approve surface, notify, why

- **Approve surface (backlog A3 decision):** terminal-first for v2.0 — a rendered review flow: bundle summary → per-oracle scenario + bound-test source side-by-side (pager) → Unspecified/Seams surfaced prominently → inline "edit" drops to $EDITOR then re-validates (P1 approve semantics) → critical tier: per-oracle ack prompts. A `--web` local HTML view is an optional stretch, not required for exit.

*(Resolved P2-14 — approve surface UX, ratified for the Opus implementation session. Every choice below is pinned; the impl session decides nothing.)*

- **Flow = the existing precondition spine + tier, then three stages.** The P1 gates run unchanged and first (parse → type conformance → lint → staleness; exits 2/3 as today). Then approve computes tier: it gains the injected `diffFacts` edge and a `--diff-base <ref>` flag exactly like verify (§2 names approve a recomputation point; the *ack obligation depends on the tier*, so this is an enforcement context — an uncomputable diff is exit 3, never "assume trivial"). The decision + facts are recorded in state.yaml's snapshot next to `change_type` (derived display, invariant 1 — CI recomputes as always) and shown in the overview header. Then: **Stage 1** overview → **Stage 2** oracle walk → **Stage 3** confirm.
- **Stage 1 — overview (one pager screen):** header line `APPROVE <change> · type: <type> · tier: <tier>` + one line of tier facts (each reason verbatim from the tier decision); then **Unspecified and Seams first** (verbatim proposal bodies — "prominently" means before any mechanics); then requirements (`REQ-id — title`), oracles (`ORC-id → REQ-id [runner: targets]`, `reproduces: true` flagged), files-to-seal — the P1 lists, unchanged in content. A zero-oracle bundle (refactor) renders the overview with the line `no new oracles — the regression suite is the correctness criterion` and skips Stage 2 entirely (the charter's ~1-minute trivial sitting).
- **Stage 2 — oracle walk, one panel per oracle in bundle order.** Left pane: the oracle's *scenario prose* — the raw `oracles.md` slice from its `##` heading through the line before its binding fence (the parser exposes each oracle's section span `[headingLine, fenceCloseLine]` + prose slice; new fields, no grammar change). Right pane: the *full source of every resolved target file* (the resolver's `targetFile`, the same bytes the seal will hash — multiple targets stacked under `── <relpath> ──` rules). Layout: two columns with a ` │ ` gutter when render width ≥ 100 (columns split the remainder equally, long lines hard-wrapped); stacked scenario-then-test below 100. Width and color are render *inputs* (CLI passes `process.stdout.columns` else 80; core stays deterministic).
- **Prompting is line-based readline** (consistent with the P1 confirm): after each panel — `[Enter] next · e edit scenario · a acknowledge (critical only) · q quit`. `a` records an in-session ack for that oracle and advances; Enter advances without acking; `q` aborts with no writes. There is no back-navigation: Stage 3 re-enters the walk for whatever remains unacked.
- **Edit loop (`e`)** — charter §Approve Session semantics, mechanized: open `$EDITOR` (fallback `vi`) at `oracles.md +<headingLine>`; on editor exit re-run the full bundle validation (parsers + type conformance + lint). Red → show findings and prompt `e` re-edit / `q` abort; a red bundle is never sealable (invariant 3). Green → byte-diff every oracle's section against its pre-edit snapshot; each changed oracle is "scenario changed after test authored": the substrate (role=propose, fresh context — invariant 10) regenerates *its bound tests only*, via the same propose-role path `--revise`/amend use, with the instruction naming the changed oracle ids; output is re-judged (invariant 2), then the unified diff of the affected bound test files (pre-edit bytes vs post-regen) renders in the pager and the human confirms it (`[Enter] accept · e edit again · q abort`). A red regeneration seals nothing — re-edit or abort. Any change to an oracle's section or bound tests **voids that oracle's in-session ack**; the generation ledger is re-stamped at seal (a green in-gate regen is a stamping point like `--revise`; an oracles.md hand-edit alone is a leaf edit, never stale — P2-05 rule).
- **Stage 3 — confirm:** `Seal <change>? N requirement(s), N oracle(s), N file(s). [y/N]`. Critical tier: while any oracle is unacked, confirm is *refused* — the unacked ids are listed and the walk re-enters at the first of them (this is "blocks confirm until all acks", literally). On seal, a critical approval.yaml records `acks: [{oracle, at}]` (optional field, schema version unchanged; absent for other tiers) — the acks are part of what the human attested, so they live in the sealed record; `verifyApproval` is untouched (acks are audit, not hash scope).
- **`--yes` is non-critical only:** trivial/standard `--yes` skips walk + confirm as today; critical + `--yes` is exit 2 ("critical tier requires the interactive gate — re-run without --yes"). Tests drive critical flows through the injected interaction edges, not `--yes`.
- **Pager & color:** all stage renders go to a string; the CLI pipes through `$PAGER` (default `less -FRX` — `-F` lets short panels flow straight through) only when stdout is a TTY, else plain write. ANSI (bold headings, dim rules, ±-colored diffs) suppressed when not a TTY or `NO_COLOR` is set.
- **Deps:** `ApproveDeps` gains `substrate` (regen), `diffFacts` (tier), and the interaction edges — pager, editor-open, oracle-walk prompt, diff-confirm — all injected; `resolve`/`confirm`/`now`/`approvedBy` unchanged. The core never touches a real terminal, editor, or clock (invariant 12).
- **Not delivered:** `--web` (the §8 stretch stays a stretch); no line-level test highlighting (the adapter protocol resolves targets to *files* — the sealed unit is the file, so the file is what renders).

*(As-built P2-14 — the shipped approve surface:)*
- **The parser exposes the span as `Oracle.prose` + `Oracle.sectionEnd`** (`line` is the heading, already present); the edit loop's change-detection compares each oracle's `prose + JSON(binding)` by id, so a whitespace-only edit regenerates nothing while any scenario/binding change (or a newly-added oracle) drives a targeted regen.
- **The interaction edges are OPTIONAL on `ApproveDeps`, not required** — the `--yes` non-critical fast path genuinely needs none, and existing `--yes` callers (amend/tracer/change-type-flow) stay untouched; the core hard-guards (`APPROVE_EDGE_MISSING`, exit 2) if an interactive path is reached without its edge. `substrate`/`diffFacts`/`config`/`model`/`width`/`color` are likewise optional; the CLI always supplies them.
- **The git diff-facts edge is shared, not duplicated:** P2-14 extracted verify.cli's inline `computeDiffFacts`/`defaultBase` into `commands/diff-facts.ts`, which both the verify and approve CLIs consume — the two authoritative recomputation points assemble the facts identically. approve's CLI reads the **working-tree** enforcement config (a local human act; invariant 7's target-branch rule is CI-only).
- **acks are `approval.yaml.acks: [{oracle, at}]`, optional, schema version unchanged** — `at` is the injected clock at ack time; `sealBundle` sorts them by oracle id for byte-stable output; `verifyApproval` never reads them (audit, not hash scope). A regeneration accepted in-gate re-stamps the generation ledger at seal (a stamping point like `--revise`), and recomputes the hash scope in case the bound-test set changed.
- **Notify hooks:** `notify/` dispatcher reading convenience config; hooks: terminal, desktop (node-notifier), webhook, github-issue/pr-comment. Fire-and-forget with logged failures (convenience-never-enforcement).

*(As-built P2-15 — the shipped notify dispatcher:)*
- **Config shape (`config.ts`).** The convenience `notify` block is four known keys — `terminal` / `desktop` / `webhook` / `github` — each a toggle (`true` = fire on all kinds; `false`/absent = off) or an object narrowing `on: [escalation|override|verify]` (default: all three). `webhook` also takes a url-string shorthand (or `{url, headers?, on?}`); `github` a target-string shorthand naming the issue/PR to comment on (or `{target?, on?}`). Parsing is **total and tolerant** (`parseNotifyConfig` never throws): an unknown key, a malformed hook value, or a bad `on:` kind becomes a warning string the dispatcher logs, and that hook is dropped — the notify block sits downstream of every enforcement write, so a typo must never block an escalation/override.
- **Two never-throw guarantees (invariant 11), proven end-to-end.** (1) *Build* never throws: `createLiveNotifier` reads the working-tree convenience config inside a `try/catch` — a malformed settings/local file disables announcements for the run (logged) rather than aborting the command that fired the event. (2) *Dispatch* never throws: `createNotifier` returns a `NotifyFn` that `Promise.allSettled`s the matching hooks, each inside a catch that logs its failure (even the log sink is guarded). A dead webhook / absent `notify-send` logs and is swallowed; the artifact on disk stays the sole blocker.
- **Producers.** escalate + amend fire the event from their cores (the P2-04 `NotifyFn` seam); **override** gained the same core seam (it became `async`, mirroring escalate); **verify** fires its `verify` event from the CLI edge (`verify.cli`) — deliberately *not* threaded through the heavily-tested deterministic verify core (invariant 12), and awaited so pending hooks complete before a red-verdict exit. verify's announcement reads the working-tree convenience config: notify is not enforcement, so invariant 7's target-branch rule does not touch the announcement channel.
- **Live edges (`runtime.ts`), behind an injected `NotifyRuntime` so the core is deterministic + testable.** terminal → **stderr** (stdout is reserved for report JSON); webhook → global `fetch` POST (non-2xx throws → logged); desktop → **shells the OS notifier** (`notify-send`/`osascript`/PowerShell) rather than pulling the `node-notifier` native dep — same effect, one fewer dependency, primitive stays injected; github → shells the ambient `gh` (`issue comment <target>`, else `issue create`) — no token plumbing in core (design §3), local-announce only (the merge-gating ratchet issue is still the CI template's job).
- **Layering.** `scripts/check-layering.mjs` gains `notify` in the middle layer (it was already in architecture.md §1's dependency direction) — `notify/` imports only `config` (same layer) + `util`; nothing imports upward.
- **`crucible why <check|ORC|R-id>`:** walks report → oracle → binding → adapter result → raw tool output path; for reviewer findings, prints rubric line + evidence + remediation.
