A verification framework for agent-built software

Approve the promise.
Let the code prove itself.

Crucible lets AI agents build software while humans approve what the software must do, not every line used to do it. Specifications and executable oracles become the reviewed contract. Deterministic verification makes the implementation answer to that contract.

01 - What

A contract-first workflow around your coding agent.

Crucible is not another model, IDE, or test framework. It is the governance and verification layer around an agent-driven development loop.

HUMAN

Approve intent

Review the specification, scenarios, scope, exclusions, seams, and executable judges at one deliberate gate.

AGENT

Author and implement

Draft the artifact bundle, then build any implementation that satisfies the approved goalposts.

MACHINE

Enforce the contract

Validate traceability, seal approved bytes, run every judge, and produce a reproducible verdict.

ELI5The answer-key version

Imagine the agent is taking an exam. It may write any answer it likes, but before it starts, you review the questions and the answer key. Then you lock the answer key. Crucible is the locked grading room: the agent cannot rewrite the questions, alter the key, skip an inconvenient question, or award itself a passing grade.

You keep your agent, language, test runner, and repository. Crucible supplies the artifact contract, the single approval gate, the tamper-evident seal, the adapter boundary, and the deterministic path from intent to merge evidence.
02 - Why

Verification effort is conserved, not eliminated.

If humans stop reading AI-written code, trust has to move somewhere better. Crucible moves it into a small, explicit trusted computing base: approved intent, executable judges, adapters, enforcement configuration, and the deterministic harness.

Crucible shrinks the trusted computing base from “all the code” to “the specs, oracles, and harness,” then concentrates human attention there.

The agent is allowed to write the code and to draft the tests that will judge it - but those judges must exist before implementation and a human must seal them. Once sealed, the implementer can freely change product code and ordinary tests, but cannot silently move the goalposts.

01

Recognition over recall

The agent enumerates requirements, scenarios, exclusions, and seams. The human spots what is missing instead of inventing every edge case from scratch.

02

Artifact authority

Files and validation decide what may happen next. Conversation history, caches, checkpoints, and “done” messages have no enforcement power.

03

One rich gate

The complete proposal - including custom artifacts and real bound tests - is reviewed once. There is no second approval ceremony after implementation.

RationaleWhy line-by-line code review stops scaling

Agent output can grow far faster than human review capacity. Keeping the old review model turns the person into the bottleneck and makes attention shallower as volume rises. Removing review entirely simply trades a visible bottleneck for invisible risk.

Crucible relocates attention to the smaller, higher-leverage surface: the promises and the checks that define correctness. One approved oracle can judge many implementations and keep judging every future change.

Deep diveHow agent-authored judges can carry trust

The agent drafts the oracle scenarios and their real test code before implementation exists. A human reviews that complete bundle, while traceability lint proves every requirement has a collected executable target. Approval then seals every relevant byte by content hash.

Trust does not come from believing the agent wrote a perfect test. It comes from separating goalpost creation from implementation, concentrating human review on those goalposts, and making later alteration mechanically visible.

03 - How

A thin lifecycle that feels like TDD.

Generated Codex or Claude Code skills steer the user’s already-active session. They call a project-local pinned CLI for status and validation. The CLI never launches a child agent.

ELI5From a chat request to a verified change

Ask your coding agent for a feature. It first writes down the promise and the tests that would prove it. You review and lock those goalposts. The same agent then writes the code. A deterministic checker runs the locked tests, and the complete change is archived before one pull request.

The oracle is prose plus a real executable check

Humans review the scenario line by line and may spot-check the test code. The linter proves every normative requirement maps to at least one oracle, every oracle maps back to a real requirement, and every binding resolves to a collected test in a contained file.

Human owns

  • Intent and acceptance of scope
  • The only approval and every amendment re-seal
  • Framework-maintenance confirmation

Active agent session owns

  • Proposal and oracle drafts
  • Conventional test-file choice and binding
  • Implementation and ordinary tests

Deterministic core owns

  • Preconditions, validation, hashes, and status
  • Adapter resolution and test execution
  • Verify, archive, and CI verdicts

When intent changes

amend validates the changed intent, custom artifacts, and bound tests together. A human reviews only the delta and mints a new seal generation.

When code changes

No amendment is needed. Product code and ordinary implementation tests remain freely editable; verification simply reruns against the unchanged goalposts.

RationaleWhy the CLI does not launch another agent

Nested agent sessions create avoidable context, sandbox, authentication, recovery, and trust problems. Crucible instead meets developers inside the agent session they already chose. Generated skills provide role guidance; the local CLI supplies deterministic status, preconditions, validation, and reports.

The conversation makes the experience pleasant, but it has no authority. If the session ends, a fresh session can recover the exact next action from artifacts alone.

Deep diveWhy archive happens before the pull request

Archiving after merge creates a second lifecycle, a second branch, and recovery states for partially completed work. Crucible archives on the feature branch after verification. Canonical specs are synced, the complete change directory is moved atomically, and the bound oracle tests stay in the product suite.

The result is one coherent pull request containing implementation, final artifacts, and the regression promise it adds to the project.

04 - Example · The tangible TL;DR

“Expire inactive sessions automatically after 30 minutes.”

One ordinary feature, followed all the way from a sentence in chat to a permanent, target-branch-verified promise. This is Crucible V2 in concrete form.

The human’s starting request
“For security, automatically expire an authenticated session after 30 minutes of inactivity. A user whose session has expired must sign in again.”
Optional explore · no authority yet

The agent turns one sentence into decisions worth reviewing.

Before creating governed artifacts, the active agent session identifies the ambiguities hidden inside “30 minutes of inactivity.” The human confirms the intended semantics:

  • Activity means a successfully authenticated request to a protected application endpoint. Health checks, failed authentication, and anonymous traffic do not refresh the session.
  • Expiry is checked before protected request logic. At exactly 30:00 since the last qualifying activity, the session is expired.
  • A qualifying request before the deadline resets that session’s inactivity window. Sessions belonging to the same user expire independently.
  • The service invalidates the expired server-side session and returns 401 SESSION_EXPIRED. A later request cannot revive it.

Absolute maximum lifetime, “remember me,” browser redirect UX, and background deletion of expired records are explicitly out of scope. The important seams - authentication middleware, session store, application clock, and multi-instance consistency - are pulled into the review instead of being left inside the implementer’s context.

Propose · agent authors, CLI validates

The request becomes a complete, reviewable artifact bundle.

Using the generated propose skill, the agent authors the OpenSpec change and real JUnit oracle tests. It chooses a conventional test file and native targets; Crucible does not authorize a path through a session handoff. The CLI only accepts the proposal when every schema-required artifact exists and every binding is contained, unique, found, and collected.

proposal.md

Why the change exists, affected behavior, explicit scope, exclusions, and rollout assumptions.

specs/session-lifecycle/spec.md

Normative requirements with stable IDs and exact boundary behavior.

design.md

Clock injection, atomic session-store update, middleware ordering, and service seams.

oracles.md

Human-readable scenarios bound to executable JUnit methods.

security-review.md

An example custom artifact required by this repository’s OpenSpec schema extension.

SessionExpiryOracleTest.java

Real test code in the product suite, written now - before approval or implementation.

### Requirement: Activity refresh [REQ-session-expiry-2]
The service SHALL refresh only that session's last-activity time after

The new behavioral tests must be red on the base revision: today’s product does not expire inactive sessions, so a test that is already green would not prove this feature. tasks.md is deliberately absent; implementation planning starts only after the goalposts are approved.

Approve · the one human gate

The person reviews the promise, not an implementation diff.

$ crucible approve automatic-session-expiry

✓ proposal and spec delta valid
✓ security-review.md present (schema extension)
✓ 3 requirements ↔ 6 oracles ↔ 6 collected JUnit targets
✓ new feature oracles are red on base

Review: scope · exclusions · seams · requirements · scenarios · bound test code
Seal this exact bundle? [y/N]

The terminal renders every schema-declared pre-approval artifact and the grounded test file. Suppose the reviewer notices that the first draft treated a background heartbeat as activity. The agent corrects the requirement and oracle before approval, validation reruns, and the person confirms the corrected bundle.

approval.yaml now records SHA-256 hashes for the proposal, delta, design, oracles.md, security-review.md, schema metadata, and SessionExpiryOracleTest.java. No agent message, skill, checkpoint, or state.yaml can mint or replace this seal. Changing one sealed byte voids it.

Implement · same active session, new role

The agent may change the solution, but not the approved goalposts.

Artifact-derived status says the change is approved and ready to implement. The implement skill’s first action is to create tasks.md; then the agent adds an injectable clock, an atomic “validate and touch” session-store operation, middleware expiry, and ordinary implementation tests. 

// Product code may change freely.
Instant deadline = session.lastActivityAt().plus(Duration.ofMinutes(30));

if (!clock.instant().isBefore(deadline)) {
    sessionStore.invalidate(session.id());
    throw SessionExpired.INSTANCE;
}

sessionStore.touch(session.id(), clock.instant());

Ordinary tests are the agent’s TDD scaffolding and carry no independent trust weight. The six approved oracle methods are different: editing, deleting, renaming, or skipping one causes a seal or oracle failure. If the approved intent itself is wrong, the path is amend plus a human delta re-seal - not a quiet test edit.

Verify · deterministic red/green

A boundary bug is caught without asking an agent whether it is done.

Imagine the first implementation uses “later than 30 minutes” instead of “at least 30 minutes.” Everything looks plausible, and most ordinary tests pass. The approved boundary oracle makes the result unambiguous:

PASSApproval hashes, adapter pin, custom artifact, and requirement traceability are intact.
PASSORC-session-001: the session remains valid at 29:59.
FAILORC-session-002: the session is still accepted at exactly 30:00; expected 401 SESSION_EXPIRED.
PASSConfigured build, unit, lint, and all archived regression suites complete.

The agent fixes the comparison in product code and reruns the same credential-free command. All six current oracles, every historical oracle, and the repository suites pass. Identical inputs produce the same machine-readable report. An agent saying “looks good,” marking the test skipped, or returning a prose self-review cannot change the verdict.

Archive · still on the feature branch

The approved promise becomes permanent project memory.

$ crucible archive automatic-session-expiry

✓ seal current
✓ deterministic verify green
✓ session-lifecycle canonical spec synced exactly once
✓ complete change moved atomically to the dated archive

The archive includes the proposal, spec delta, design, oracles.md, tasks.md, approval history, security-review.md, schema metadata, and every other extension or extra artifact. The JUnit oracle file stays in the product test suite. Archiving registers it as a regression promise; there is no second archive-only PR or post-merge recovery lane.

One PR · target-owned enforcement

The candidate brings the work; the target branch brings the judge.

The feature PR contains the implementation, ordinary tests, complete archive, and new oracle test. The required CI workflow evaluates it using the target branch’s enforcement configuration, exact verifier and adapter pins, and all previously archived oracle inputs. Candidate edits to those trust files are inert for this candidate’s own evaluation.

  • The candidate runs without secrets, write permission, persisted credentials, or privileged cache.
  • Deterministic verify is the required merge authority and needs no LLM API key.
  • Optional ai-review remains separately off, advisory, or required.
  • A later authentication refactor must still pass these six session-expiry oracles automatically.
The whole framework in this example: the agent expands intent and writes real judges; the human reviews and seals them once; the agent implements against immovable goalposts; deterministic machinery catches the exact-boundary bug; archive turns the feature into permanent regression memory; target-owned CI - not the candidate - decides whether it may merge.

05 - Trust

The agent’s self-report is worth zero.

These rules define Crucible even when no convenience UI is available. Violating one is a framework bug, regardless of how many unit tests pass.

ELI5The goalposts stay put

Once you approve the rules of the game, the player cannot move the goalposts, dismiss the referee, skip a difficult play, or declare victory. Crucible treats every broken or missing judge as a loss, then explains exactly which rule was not satisfied.

01

Artifacts are truth

Status is derived from validated artifacts. A cache or conversation cannot authorize a transition.

02

Self-report is zero

“Done” means an artifact exists and validates or a named check passes - never that an agent says so.

03

Fail closed

Malformed, missing, ambiguous, unresolvable, or unparseable inputs fail instead of warning or skipping.

04

Skip equals fail

A skipped oracle is a failed judge. Missing results and uncollected targets are also red.

05

Preconditions teach

Every command checks its prior-stage artifact and names the exact corrective action when blocked.

06

Hashes seal

Every approved artifact and grounded bound test is content-hashed. One changed byte voids approval.

07

Target branch judges

A PR cannot select the enforcement config, framework pin, adapter pin, or historical inputs that judge it.

08

Policy is computed

If proportional tiers return later, they are recomputed from facts, can be forced up, and can never be forced down.

09

Review is enumerated

Optional AI review may block only on known rubric IDs. Unknown concerns are observations, not invented law.

10

Role context is explicit

Generated skills provide role instructions and artifact context; conversation history is convenience, never evidence.

11

Convenience is not enforcement

Skills, notifications, watch mode, and status displays may fail without turning red into green or green into red.

12

The core is deterministic

Everything except proposal, implementation, and optional AI review is reproducible from identical inputs.

RationaleWhy a skipped oracle is a failure

A skipped judge says nothing about the product. Treating it as neutral would make disabling an inconvenient oracle the cheapest path to green. Crucible therefore fails on skipped, missing, uncollected, malformed, or incomplete oracle results.

Deep diveCurrent oracles, ordinary tests, and regression

Current-change oracles prove the implementation honors newly approved intent. Ordinary tests help the agent design and debug the implementation, but the agent may edit them freely, so they carry no independent trust weight. Archived oracle tests form the regression suite and prove that past promises still hold.

This separation is why a pure refactor needs no invented feature oracle: its contract is the unchanged specification plus the accumulated regression suite.

06 - Architecture

One protocol, many ecosystems.

Crucible is a TypeScript/Node monorepo built on OpenSpec’s artifact format. It is a layer, not a fork. Core never imports a test framework; separate adapter executables speak strict JSON over stdin/stdout.

Project-local distribution

Each consumer pins exact Crucible bytes, a packaged supported OpenSpec runtime, built JavaScript exports, and adapter content hashes. There is no ambient executable fallback.

Generated agent surfaces

Codex and Claude Code receive generated skills or commands from one provider-neutral definition. They steer the active session but do not become workflow state.

Frozen adapter boundary

resolve proves targets exist and are collected; run emits normalized results. Malformed transport or dependency discovery aborts.

ELI5Adapters are translators

Crucible asks, “Does this named check exist?” and “Did it pass?” An adapter translates those two questions into the native language of JUnit, pytest, Cargo, or another test runner, then translates the result back into one strict format.

Archive means the whole change, not a curated subset

Before the feature PR, archive revalidates and atomically moves the complete OpenSpec change: proposal, specs, design, oracles.md, tasks.md, approvals and amendments, .openspec.yaml, every artifact added by schema extensions, and any unknown extra files. Bound oracle test code remains in the product suite and becomes permanent regression input.

The first reference adapter is Java/JUnit

The reference adapter targets JUnit 5 through Maven and Gradle, including dependency-backed discovery for Spring MockMvc and other real classpath-dependent tests. A stub adapter provides protocol and generic lifecycle conformance. Additional adapters can cover Python, TypeScript, Rust, and other ecosystems without teaching core about their test frameworks.

RationaleWhy adapters are separate executables

Keeping adapters out of core prevents one ecosystem’s assumptions from leaking into every project. The JSON stdin/stdout boundary also makes adapters independently packageable, pinnable, testable, and replaceable.

Deep diveWhy an adapter belongs in the trusted computing base

An adapter decides whether an executable judge was found and whether it passed. Compromising that decision collapses the verification story, so adapters are pinned by version and content hash, immutable during implementation, and certified against conformance fixtures.

07 - Trusted CI

The candidate never chooses its own judge.

Local verify is fast advisory feedback. Merge authority comes from the same deterministic verification rerun in CI using enforcement inputs taken from the exact target branch - not from the incoming PR.

ELI5The home team cannot bring its own referee

A pull request is allowed to bring new code and new proposed promises. It is not allowed to bring a weaker rulebook, a friendlier verifier, or a replacement scoreboard for judging itself. Those come from the branch the change wants to enter.

Trusted base inputs

  • Enforcement configuration
  • Exact framework verifier pin
  • Exact adapter pins
  • Historical specs, oracles, tests, and harness
  • AI-review policy and rubric, if enabled
→

Untrusted candidate inputs

  • Product implementation
  • Ordinary tests
  • The proposed approved change and new oracle tests
  • Any proposed edit to a trust file

A proposed trust-file edit is treated only as candidate data while that PR is evaluated. After an independently authorized merge, it may govern later PRs. This prevents a PR from weakening the rule, verifier, adapter, or workflow that evaluates that same PR.

Preferred organization deployment

An organization or enterprise ruleset requires a workflow stored in a separately trusted repository. It runs on ordinary restricted pull_request, checks out exact base and head separately, and also handles merge_group.

Candidate execution constraints

No secrets, write token, persisted checkout credentials, privileged cache, or persistent runner. A candidate job with the same check name cannot satisfy the trusted required workflow.

What enforcement-grade CI must establish

TRUST INPUTS

Exact base-owned judge

Configuration, framework verifier, adapter pins, historical oracle inputs, and optional reviewer policy come from the target branch.

EVENT BINDING

Exact base and candidate commits

The workflow handles same-repository heads, forks, and merge queues without confusing which bytes are trusted.

ISOLATION

Restricted candidate execution

Candidate code receives no secret, write token, persisted checkout credential, privileged cache, or persistent runner.

AUTHORITY

A required check the candidate cannot spoof

A same-name workflow in the pull request cannot replace the independently required verifier.

HONESTY

Protection grade is visible

doctor --ci distinguishes ruleset or App enforcement from a repository-local workflow that is only advisory.

RationaleWhy configuration comes from the target branch

If a candidate could choose the policy, verifier, adapter, or historical suite used for its own evaluation, it could weaken the judge in the same change that needs approval. A trust-file edit is therefore treated as untrusted candidate data now; once independently merged, it may govern later pull requests.

Deep diveWhy pull_request_target is not the default

Candidate code must run, but it must not run inside a privileged workflow context. The preferred organization deployment uses an independently required workflow on ordinary, restricted pull_request, with exact base and candidate checkouts. pull_request_target candidate execution remains rejected unless a separately reviewed threat model proves a narrowly bounded use.

09 - Questions

Questions worth asking.

Does Crucible’s CLI run Codex or Claude Code?
No. Open Codex or Claude Code in the initialized project and use the generated Crucible skills or commands. Those surfaces guide the active session and call the pinned project-local CLI for deterministic validation; Crucible does not launch a child agent.
Who chooses the oracle test file and binding?
The authoring agent chooses a conventional path and native target during propose. The CLI does not authorize a candidate path or pass a candidateFile handoff. It validates containment, uniqueness, collection, grounding, and red-on-base behavior where required.
Can the implementer change a bad oracle?
Not directly. A sealed edit blocks implementation and verification. If the approved intent is wrong or incomplete, the agent uses amend; a human reviews the exact intent/test delta and mints a new seal. Ordinary code fixes need no amendment.
Does verification require an LLM API key?
No. Deterministic verify is the required check and never calls a model. AI review is a separate optional feature with off, advisory, and required modes.
Is local green authoritative?
No. Local verification is fast feedback on an agent-controlled machine. Enforcement-grade merge authority requires target-owned CI. doctor --ci reports whether the repository actually has ruleset or App protection, or only an advisory local workflow.
Why not use pull_request_target?
Because executing untrusted candidate code in its privileged context is not accepted as the default design. The preferred path is an organization-required workflow on ordinary restricted pull_request. Any future bounded use requires its own threat model and ratification.
What happens to custom OpenSpec artifacts during approval and archive?
Schema-required pre-approval artifacts enter the approval candidate set and seal automatically. Archive preserves those extensions - and unknown extra files - alongside oracles.md, approvals, amendments, tasks, specs, and design. The archive is schema-complete, not a hard-coded shortlist.
