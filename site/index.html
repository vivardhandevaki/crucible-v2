Never read the code.

Crucible is a framework for building software end-to-end with AI agents, where the human's job moves from approving code to approving intent — and deterministic machinery guarantees the code honors it.

One human gate. Five commands. Agents write the implementation and draft the judges — but a person seals the judges before any code exists, and after that, the only path to green is through the code.

extended TDD/BDD, not a bureaucracy one human gate: approve oracles precede implementation tech-agnostic via adapters
01 — Purpose & thought process

Why Crucible exists

The problem isn’t that AI can’t write the code. It’s that verification effort is conserved, not eliminated — so the verification had better be enjoyable to live inside.

ELI5

AI can write most code now, but somebody still has to make sure it's right. Reading every line yourself is too slow — you'd lose the whole speed advantage. So Crucible's trick, from day one: the AI takes the exam, but a person approves the answer key first. One answer key can grade a thousand exams the same way, instantly.

The obvious way to enforce that is to build a fortress — guards at every door, cameras in every corner, forms in triplicate. Fortresses work, and nobody wants to go to school there, so they quietly stop being used. Crucible keeps exactly two hard things — the answer key and the locked grading room — and makes everything else feel like a normal school day: you check the answer key once (about ten minutes), and everything after that is automatic.

The premise: verification effort is conserved, not eliminated. If humans stop reading code, trust must come from machine-checkable verification. Humans author and approve intent artifacts — specs and oracles. Agents author implementation. Deterministic infrastructure enforces the workflow.

The whole architecture in one sentence: Crucible's job is to shrink the trusted computing base from “all the code” down to “the specs, oracles, and harness” — and then concentrate scarce human attention exclusively there.

The two naive responses — and the design requirements that follow

Naive response #1: keep reviewing everything. Humans read every AI-written PR line-by-line. The human becomes the bottleneck, the speed advantage evaporates, and review quality decays with volume anyway — fatigue is not a security model.

Naive response #2: stop reviewing, just trust it. Model + linters + its own tests. But code and tests written by the same mind share the same blind spots, agents under optimization pressure game their own checks, and “nobody looked” is not the same thing as “it’s right.” Unchecked ≠ trusted.

The resolution: relocate trust from the output to the judges. Agents draft both code and judges — but a human seals the judges first, and machinery guarantees the code answers to them. From that follow four design requirements, in priority order: (1) guarantees enforced by machinery, never by vigilance — the workflow lives in artifacts and CI, not in anyone’s discipline; (2) a developer experience people choose voluntarily — a framework nobody enjoys using enforces nothing; (3) language- and stack-agnosticism, so the guarantees aren’t one ecosystem’s privilege; (4) honesty about limits — every guarantee machine-checked, and everything that can’t be guaranteed is named, not implied.

Two standing tests then govern every feature: does this ask the human for information the system could compute, or attention the system could defer? (if yes, it’s a DX bug) — and the meta-rule: every convenience must be computed deterministically from artifacts, never self-declared by an agent, or by a human under deadline pressure.

The failure modes it's designed against

  • Reward hacking. An agent that can touch its own tests will “pass” them. In Crucible the oracles are sealed by hash before implementation starts; the implement agent literally cannot modify what judges it, and a skipped test counts as a failed test.
  • The grading-your-own-homework loop. If one pipeline writes the spec, the oracles, and the code with no human touch, “correct” collapses into “internally consistent.” Crucible's single human gate at approve breaks the loop exactly once, where leverage is highest.
  • Improvised decisions. Ambiguity discovered mid-implementation is a spec bug. Agents must stop and escalate — never guess — and the fix flows through a thirty-second amend, so the decision lands in the spec forever instead of in one agent's context window.
  • Judgment under deadline pressure. Humans asked to pick “how much verification does this change need?” at 6 PM on a Friday will pick wrong. So tiers are computed from observable facts, and can be forced up but never down.
  • Silent decay. Every escaped defect must ship a permanent commit — a new oracle, rubric line, or rule. The system only ratchets stricter.
Example: why the agent's own green tests prove nothing
the code (has a bug: forgets quantity)
Money refundFor(Item item, int qty) {
  return item.price();            // BUG: should be price × qty
}
the agent's own unit test (encodes the SAME misunderstanding — passes anyway)
assertEquals(item.price(), refundFor(item, 3));  // green ✓ … and wrong
the human-approved oracle, written before the code existed
assertEquals(item.price().times(3), refundFor(item, 3));  // red ✗ — bug caught

Code and test written by the same mind share the same blind spots — that's true for humans and doubly true for a model with one context window. Splitting who writes the judge from who writes the code, with a human seal in between, is the entire trick.

02 — A shared vocabulary

Seven words that carry the whole system

Learn these and every diagram below reads itself. Full definitions live in the dictionary.

ELI5

An oracle is the answer key: “given this, when that, then this must happen” — plus a real test that checks it. A spec is the list of promises your software makes. A tier is how careful the system is with a change (a typo fix and a payments change are not treated the same). An adapter is a translator so Crucible can run tests in any language. The ratchet means every escaped bug makes the rules permanently stricter — the system only tightens, never loosens.

Oracle

A human-readable scenario (Given/When/Then) bound to an executable test. The judge. Established testing-literature term: the mechanism that decides whether output is correct.

Spec delta

The change's new promises — SHALL statements with stable IDs like [REQ-auth-lockout-1]. A requirement without an oracle fails the build: it's a wish, not a spec.

Approval

The one human gate. Sealed as approval.yaml: SHA-256 hashes of every approved artifact and bound test. Any later edit voids it automatically.

Tier

trivial · standard · critical — computed from facts (spec delta? risk paths? diff size?), never chosen. Scales ceremony and merge routing, never the safety net.

Adapter

A pinned, hash-locked executable that resolves and runs tests for one runner (JUnit, pytest…). Core never understands any test framework; adapters translate.

Ratchet

Every escaped defect's fix must ship a reproduction oracle (proven red on the old code, green on the fix). Every agent failure ships a harness fix. Monotonic strictness.

TCB

Trusted computing base: the small set that must be trusted — specs, oracles, rubric, adapters, harness, CI. Everything the implement agent cannot touch, which is why it can be fully untrusted.

What an oracle actually looks like

One markdown file, oracles.md, in the change bundle. Humans read the prose; the linter reads only the fenced block; the two live inches apart so drift is visible at the gate.

oracles.md — one oracle, both halves
## ORC-lockout-001: Fifth failure locks the account
**Given** an account with 4 consecutive failed login attempts
**When** a 5th attempt fails
**Then** the account is locked and correct-password logins are rejected

```yaml crucible-binding
requirement: REQ-auth-lockout-1
kind: unit
runner: junit
target: com.acme.auth.LockoutTest#fifthFailureLocks
```

The bound test is real code, written by the propose agent before approval, covered by the approval hash, immutable afterwards. The traceability linter enforces three-way integrity in milliseconds: every REQ ↔ at least one ORC ↔ a test that actually exists and runs.

Why “unit tests carry zero trust” is a feature, not an insult

The implement agent writes and edits its own unit tests freely — they're its red-green scaffolding, the same way a human TDD practitioner uses throwaway tests to think. Nothing about merging depends on them, so there's nothing to game. Judgment comes only from things the implement agent can't touch: this change's sealed oracles, and every previous change's oracles (the regression suite). That split is also what makes refactors safe: a pure refactor needs no new oracles — its correctness criterion is simply “every past promise still passes, and the spec is untouched.”

03 — Principles

The constitution

Eight invariants. Violating any of them is a bug, no matter how green the tests are.

ELI5

The rules of the game: the robot that writes the code can never touch the things that grade it. Nobody gets to say “trust me, it's done” — done means the checker says so. If a form is filled out wrong, the answer is “no,” not “probably fine.” And when anything is unclear, the robot must stop and ask a person — guessing is against the rules.

1 · Artifacts are truth

The workflow's state is the files on disk. state.yaml is a derived audit log; editing it changes nothing. Hand-offs are artifacts, never messages.

2 · Self-report is worth zero

“Done” = the artifact exists and validates / the named tests pass. An agent's claim of completion — including a confident one — carries no weight anywhere.

3 · Fail closed, everywhere

Malformed JSON, unparseable artifacts, a broken adapter, a skipped oracle test — all are failures, never warnings. A skipped judge is the cheapest hack there is, so skip = fail.

4 · Preconditions gate every command

Each command refuses to run unless the prior stage's artifact exists and validates — and its error names the exact next command. Errors teach the workflow.

5 · Hashes seal; TCB is untouchable

approve seals content hashes of everything reviewed. Post-approval, any edit to specs, oracles, or bound tests voids the approval automatically. TCB paths are immutable to the implement agent.

6 · Computed, never declared

Tiers, routing, and every other convenience are derived from observable facts. You can force a tier up, never down. Rules that judge a PR come from the target branch, not the PR itself.

7 · The reviewer may not invent rules

The AI reviewer blocks only on enumerated, versioned rubric lines. Everything else it notices becomes an observation — harvested for the ratchet, never a veto.

8 · Convenience is never enforcement

Notify hooks, slash commands, status displays can all fail without blocking or unblocking anything. Deleting every convenience leaves the workflow enforced — just tedious.

Why one gate — isn't a second review after the tests are written safer?

It sounds safer, but Crucible already is test-first at the gate: when you run approve, the scenarios and their executable test code both already exist, rendered side-by-side in one sitting. Implementation starts from red, TDD-style. A second gate after “oracle code is written” would show you nothing the first gate doesn't already contain — it would just double interruptions. And moving oracle authoring into the implement step to justify that second gate would hand the judges' pens to the judged. So: one gate, made rich — side-by-side rendering, per-oracle acknowledgment on critical tier, and mutation testing as the mechanical backstop against vacuous tests that no amount of human reading catches anyway.

Example: “computed, never declared” in one exchange 
# the agent (or you) claims a one-line payments change is trivial…
$ crucible propose "fix rounding in refund display" --tier trivial

# CI recomputes from facts: the diff touches payments/**
✗ tier mismatch: claimed trivial, computed critical (risk glob: src/**/payments/**)
→ re-run without --tier; critical ceremony applies (it's a payments change)

Nobody argued. Nobody decided under pressure. A glob matched a path, and the answer was the same on every machine, every time.

04 — Architecture

How it's built

Five stateless commands. One human moment. Two venues with one truth.

ELI5

Think of a relay race where the baton is a folder of files. Each runner (agent) picks up the folder, does exactly one job, puts new files in, and leaves. No runner remembers anything, and no runner can start unless the previous runner's files are actually there and correct. In the middle of the race, one human checks the plan — after that, machines carry it home. Your laptop is for practicing; the stadium (CI) is where results count.

Local vs. CI — feedback vs. enforcement

The split is not “different checks in different places.” It's the same verify command in two venues with different authority. Your machine is agent-controlled and therefore untrusted: local green is a signal. CI re-runs everything — plus the full regression suite, hash checks, tier recomputation from target-branch config, and the adversarial reviewer — and only CI's verdict counts. That's what keeps the core property alive: the only path to green is through the code.

Configuration: three files, three protection levels

The target-branch rule — self-referential tamper-proofing for free

One sentence: the rules that judge your PR are the rules already on main. CI reads enforcement config from the branch being merged into, never from the PR. So an agent that edits the risk globs to downgrade its own change achieves nothing — its edit isn't law until it merges, and merging a crucible.yaml change is itself a critical-tier, human-reviewed event (the file sits in its own risk globs). Bonus: when the team tightens a rule on main, it applies instantly to every open PR — no stale per-change snapshots.

Adapters — how one framework speaks every language

Crucible's core never imports a test framework. Oracle bindings name a runner (junit, pytest…) and an opaque target in that runner's native addressing; a pinned adapter — a separate executable speaking JSON over stdin/stdout — honors two verbs: resolve (do these targets exist? no execution) and run (execute, return normalized results). Adapters map to runners, not frameworks: one java-junit adapter covers plain Java, Spring Boot, Quarkus — a @SpringBootTest with Testcontainers is just a slow JUnit test. Adapters are TCB: version- and content-hash-pinned in a lockfile, certified by a conformance suite, and installed exactly once — at init. After that, the configuration is the repo: a teammate who clones runs nothing.

The adversarial reviewer — bounded judgment

A stateless, fresh-context AI reviews every diff against a versioned 12-line rubric (.crucible/rubric.yaml) — vacuous assertions, weakening in oracle-measured paths, swallowed errors, timing hacks, decisions the spec doesn't determine, out-of-scope hunks… Its verdict is strict JSON, fail-closed three ways: malformed output = fail; “fail” with no blocking finding = fail; citing a rubric line that doesn't exist = fail. It's the system's one nondeterministic gate, so it's kept on a leash: it can block only on the enumerated list; novel concerns go to an observations channel for humans to promote into rubric lines. The rubric grows into the executable form of your institutional knowledge — “monetary amounts are never floats,” “webhook fields are never removed, only deprecated.”

05 — Under the hood

What actually happens when you run a command

No magic — every step is a file appearing, a hash matching, or a check exiting 0 or 1.

ELI5

Every command does three things: check that the previous step's files are really there and really correct, do its one job, and write its own files down. If anything's missing, it refuses — and tells you exactly which command to run instead. That's why nothing ever gets “stuck in someone's head”: the head is the folder.

Each command, mechanically

  1. propose · Agent

    Scaffolds the change bundle, spawns a fresh-context agent with the propose role prompt. The output is then judged, not trusted: parsers validate every artifact's grammar, the traceability linter checks REQ↔ORC↔test integrity, the adapter dry-runs resolve on every binding. Red → the propose fails before you ever see it. The bundle must include an explicit “Unspecified / out of scope” section and a “Seams” list (systems touched, contracts crossed) — ambiguity is surfaced to you, not expected from you.

  2. approve · You — the one gate

    Renders the bundle as one review surface: scenarios and their bound test code side-by-side, Unspecified and Seams up top. Edit anything inline → the affected bound test is regenerated and its diff shown → validators re-run. Confirm → approval.yaml is written with SHA-256 hashes of every artifact and bound test file. On critical tier, each oracle needs an explicit acknowledgment. Reviewing declarative scenarios exploits recognition over recall: you're bad at enumerating edge cases from scratch, and very good at spotting the missing one in a list.

  3. implement · Agent (separate context)

    Refuses without a valid approval (exit 2: “run crucible approve”). Generates tasks.md as its first action — the work breakdown is downstream of the gate, not review material. Then plain red-green TDD against the sealed oracles: code → local verify → read machine-parseable failures → fix → repeat → push. Hits ambiguity? It files escalation.yaml and stops; implement cannot resume while it's unresolved.

  4. verify · Script

    A deterministic pipeline, not an agent: parse bundle → traceability lint → adapter runs (this change's oracles + the regression suite) → approval-hash check → tier recomputation → (in CI) static suite, reviewer verdict, routing decision → one aggregated report, exit 0 or 1. The AI reviewer's verdict is one input to this script — never the script itself.

  5. amend / override · You, rarely

    amend: shows approved-vs-current diff (or the escalation's options), you pick/edit, affected artifacts + tests regenerate, you confirm that diff, a delta entry with fresh hashes is appended. Thirty seconds; the decision now lives in the spec forever. override: works instantly at 2 AM but is loud — CI forces human review regardless of tier and auto-files a ratchet issue that stays open until a retroactive proposal lands. Bypass is possible, visible, and self-repairing — because a prohibition that can't survive an outage just gets forked silently.

06 — Proportional ceremony

Tiers: a typo fix is not a payments change

Uniform ritual is how good processes get abandoned. Crucible scales the ceremony — never the safety net.

ELI5

Moving furniture inside your house? Quick nod. Adding a room? Proper plan, one real review. Touching the electrical panel? Full inspection, and a person signs off at the end no matter what. You don't choose which one applies — the house rules decide from what you're actually touching. And in every case, all the smoke detectors stay on.

Three rules keep the table honest: a risk-glob match always wins (a “trivial” one-liner in payments/** is critical); a spec delta guarantees at least standard (new promises always get oracles and a real gate); and the executed-checks row barely varies by design — every tier still runs the full regression suite, the static suite, and the reviewer. Tiers scale authoring ceremony and merge routing. The safety net is not a dial.

07 — How to use it

From an empty repo to shipping features

One interactive setup, ever. Then a loop of three commands you'll actually enjoy.

Part 1 — One-time project setup

ELI5

You answer questions once — “found your Java project, use the JUnit adapter?” — and Crucible writes everything down as normal files in the repo. That's the whole trick: because the setup is the files, a teammate who clones the repo sets up nothing. It's already configured for them.

  1. Initialize · You

    Detects your stack, proposes adapters (“Found pom.xml → java-junit v1.x — pin it?”), writes the config trio, installs the schema bundle, role prompts, default rubric, and CI workflow — then smoke-tests the adapter so misconfiguration surfaces now, not at first propose.

    Terminal: crucible init

  2. Edit the risk globs — deliberately · You

    The one config that matters: which paths are critical. Defaults cover auth, payments, migrations, dependency manifests, CI, and Crucible's own files — tune them to your product's real risk surface. This is the dial the whole routing system reads.

    File: crucible.yaml → risk.critical: ["src/**/payments/**", …]

  3. Turn on branch protection · You

    Make crucible verify a required check and enable auto-merge. From here, enforcement lives in the platform — deleting every convenience tool leaves the workflow enforced, just tedious.

Part 2 — The everyday loop

ELI5

Say what you want → read the plan and the answer key for ten minutes → say yes → go get coffee. If the robot gets confused, it stops and asks you one question. If everything's fine, the change merges itself and its tests guard the codebase forever.

  1. Explore (optional) · You + agent

    Chat freely in Claude Code / your editor — half-formed ideas, dead ends, tangents. Nothing here is binding. When you're decided, the slash command distills the conversation's intent and hands it to the CLI; the artifact author always starts with a clean context plus your decisions.

    Chat: /crucible:propose  ·  or Terminal: crucible propose "lock account after 5 failed logins"

  2. Approve — your ten minutes · You

    Read the scenarios like a PRD, glance at each bound test beside its scenario, check the Unspecified section for decisions the agent surfaced, fix anything inline. Confirm → sealed. This is the last time you're needed unless something routes back.

    Terminal: crucible approve

  3. Implement + verify · Agents & scripts

    Unattended. The agent red-greens against the sealed oracles and pushes; CI re-verifies everything and routes the merge by tier. You get pinged only for escalations (Slack/desktop, your choice) and critical-tier reviews.

    Terminal: crucible implement  ·  then: git push

  4. When reality bites · You, 30 seconds

    Escalation? crucible amend — pick an option, confirm the regenerated diff, the loop resumes, and the decision is in the spec permanently. Production incident? crucible override ships now and files its own debt. Lost? crucible status always ends with the exact next command.

08 — Worked examples

Three changes, end to end

A normal feature, a refactor, and a critical change where everything goes sideways — which is where the framework earns its keep.

① Standard feature: “Lock accounts after 5 failed logins”

you type one line; the agent drafts the whole bundle
$ crucible propose "lock account after 5 failed logins, 15-min cooldown"

$ crucible status
  change: account-lockout   tier: standard (computed: spec delta, no risk paths)
  ✓ proposal ✓ spec-delta ✓ design ✓ oracles (7, all bindings resolve)
  ✗ approval — next: crucible approve

At approve, the Unspecified section surfaces a real product decision — “does a successful login reset the counter? assumed yes.” You realize a flagged account shouldn't fully reset, edit the scenario inline, the bound test regenerates, you confirm. Sealed. implement runs unattended; CI re-verifies all of it (oracles, full regression, hashes, reviewer, trajectory) and — standard tier, all green — auto-merges. On archive, the 7 oracles join the permanent regression suite.

Your total involvement: one sentence of intent, ten minutes of reading, one scenario fixed. Zero code written, zero code read.

② Pure refactor: “Extract retry logic into a shared module”

$ crucible propose "extract duplicated retry logic from payment + email clients"
  type: refactor · tier: trivial (no spec delta — promises nothing new)
  bundle: 1-paragraph proposal · no new oracles

Approval takes a minute: “moving code, promising nothing new.” But trivial skipped only the authoring ceremony — CI still runs the entire accumulated regression suite. If the refactor subtly changes retry timing that any past oracle ever pinned → red, routed back. This is the maintenance unlock: the “too risky to touch” refactor is finally safe, because every past promise is executable.

③ Critical path, things go sideways: “Partial refunds”

$ crucible propose "support partial refunds on orders"
  tier: critical (risk glob: src/**/payments/**) · 12 oracles incl. property tests
  seams: ledger service · merchant webhook contract

Mid-implementation the agent hits a question the spec doesn't answer — are fees recalculated on partial refunds? It does not improvise: 

$ crucible status
  ⚠ ESCALATION: ORC-refund-007 underspecified — fee handling on partial refund
    options: (a) proportional recalc  (b) no fee refund  (c) flat re-fee
  next: crucible amend

$ crucible amend        # you pick (a); spec + oracle + test regenerate; you confirm the diff
  ✓ approval re-sealed (delta #1) — implementation resumed

Thirty seconds, and the decision now lives in the spec forever. CI adds critical-tier extras — blocking mutation testing catches one vacuous assertion; the reviewer's verdict cites the exact rubric line and remediation; the agent fixes it next iteration. All green — but critical tier never auto-merges: the PR routes to you with a focused summary. You review this one because the router decided it matters.

Two weeks later a customer hits an escaped edge case (refund against a disputed charge). The fix is a bugfix-type change whose schema mechanically requires a reproduction oracle, verified red on the pre-fix commit, green on the fix — CI-checked, no honor system. The fix cannot merge without permanently encoding the failure: ORC-refund-013 joins the regression suite. That exact regression is now impossible, forever, for every future change. That's the ratchet.

The pattern across all three: your commands were propose → approve → implement, plus amend when reality bit. Tiers, hashes, routing, and the gauntlet happened to the change, not by you — and at every moment, crucible status could tell you exactly where things stood, because the state is the files.

09 — FAQ

Frequently asked questions

Q Isn't this just TDD with extra steps?

It's TDD's shape — tests exist and are red before code — extended in three ways: the scenarios are business-readable (the BDD half), a human seals the tests before implementation so the coder can't bend them, and the accumulated tests of every past change form a permanent, executable contract. Classic TDD trusts the same person to write test and code; Crucible assumes the coder is an untrusted agent and splits those roles with a hash between them.

Q The AI writes the oracles too. Isn't it grading its own homework?

It drafts the exam; it never grades its own. Three separations do the work: the propose agent and implement agent are different, fresh-context invocations; a human reviews and seals the oracles between them; and after sealing, the implement agent can't modify a single byte of them (hash + CI check). Add mutation testing — which checks whether the tests would even notice a bug — and vacuous oracles get caught mechanically too.

Q Why review artifacts instead of just reviewing the code?

Leverage and human nature. A scenario list is declarative — you verify it against intent, which only you have. Code review verifies against the spec you're holding in your head, line by line, and fatigues in minutes. And one reviewed oracle grades every future version of the code automatically; one code review grades exactly one diff, once. Reviewing the judges scales; reviewing the output doesn't.

Q Do I really need new oracles for a refactor?

No — and this is a rule, not a courtesy: oracles are triggered by spec deltas, not code changes. A pure refactor promises nothing new, so its correctness criterion is simply “every past oracle still passes and the spec is untouched.” The honest residual: behavior no past oracle ever pinned can drift unseen. That's a coverage gap — exactly the escape class the ratchet exists to close.

Q What physically stops the agent from editing the tests?

Layers. approval.yaml stores content hashes of every oracle and bound test; CI recomputes them, so any edit voids the approval and the PR fails. Diffs touching oracle paths after approval fail a dedicated check. A skipped test counts as failed. Even the attempt shows up in the captured session trajectory. And enforcement config itself is read from the target branch, so editing the rules in the PR is inert. The agent's cheapest path to green really is: write correct code.

Q What if the spec itself is wrong or incomplete?

Then Crucible can't save you from shipping the wrong thing — it verifies code against approved intent, not against the market. What it does do: force the propose agent to surface an explicit “Unspecified / out of scope” list and a “Seams” list at the gate (you're far better at spotting a missing case in a list than enumerating from scratch); force agents to stop and escalate on mid-flight ambiguity; and turn every escaped defect into a permanent oracle. Spec completeness is attacked, honestly, as a ratchet — not claimed as a guarantee.

Q Why can the AI reviewer only block on a fixed rubric? Let it use its judgment!

Because it's the one nondeterministic gate in the system. Open-ended veto means the same diff passes Tuesday and fails Thursday, blocks become unfalsifiable (“this feels fragile”), and the implement agent can't learn the rules it's judged by. So: what can stop a merge is a fixed, versioned, human-owned list — and everything else the model notices flows to an observations channel, where humans promote the good ones into new rubric lines. Its judgment is harvested, not handed a veto.

Q What happens at 2 AM when production is down?

crucible override "payment outage" — it works instantly, on purpose. But it's loud: CI forces human PR review regardless of tier, and a ratchet issue is auto-filed that stays open until a retroactive proposal lands. A rule that says “no exceptions, ever” is exactly the kind that gets violated silently — once, and then forever. Crucible’s bet: visible, self-repairing bypass beats theoretical impossibility.

Q Doesn't the human gate become the new bottleneck?

It's ten minutes of reading per feature — deliberately the only synchronous human moment — and it's proportional: trivial changes gate in about a minute. Compare against the alternative it replaces: reviewing every PR line-by-line, forever. The gate concentrates your attention where one sitting has permanent leverage (the judges), and everything else runs while you do something better.

Q Are the implement agent's unit tests pointless, then?

Not pointless — trustless, and those differ. They're the agent's scaffolding for building, exactly like a human's throwaway TDD tests, and they make it faster and better at converging on green. They just carry no weight in the merge decision, because the agent can edit them at will. Judgment comes only from what it can't touch: this change's sealed oracles and every past change's regression suite.

Q What languages and frameworks does it support?

Anything with a test runner, via adapters — which map to runners, not frameworks. One java-junit adapter covers plain Java, Spring Boot, Quarkus, Micronaut (a @SpringBootTest with Testcontainers is just a slow JUnit test). Adapters are small, separate executables (~a few hundred lines), certified by a conformance suite, pinned by content hash. First-party: java-junit first, Python/TypeScript next; the community covers the long tail.

Q How does this relate to OpenSpec? Is it a fork?

A layer, not a fork. Crucible consumes OpenSpec's artifact conventions — specs/ as current truth, changes/ as proposed deltas, custom schemas for the artifact sequence — and adds everything OpenSpec deliberately doesn't have: oracles, the approval gate and hashes, the traceability linter, the verify runner, tiers, routing, the reviewer, and the CI enforcement half. OpenSpec upgrades are handled by a repeatable two-command procedure (openspec update + crucible doctor).

Q How is this different from “AI coding plus a good test suite”?

Four things an ordinary suite doesn’t give you. Ordering: tests written after (or alongside) the code inherit its blind spots; Crucible’s judges exist and are sealed before implementation starts. Custody: nothing normally stops the coder — human or agent — from editing an inconvenient test; here that voids the approval and fails CI. Bookkeeping: a suite can’t tell you which requirements have no test at all; the traceability linter makes a requirement-without-oracle a build failure. Memory: ordinary suites decay because nothing forces them to grow; here every archived change’s oracles join the permanent regression suite, and every escaped defect must add one. Same ingredients — tests, CI — arranged so the cheapest path to green is correct code.

Q What does Crucible not guarantee?

Honesty corner: it can't verify intent it was never told (spec completeness is ratcheted, not solved); property and contract tests approximate correctness, they don't prove it; emergent behavior between independently-verified features is only partially addressed (the seams section drags it into review); and the first instance of a genuinely novel failure class can escape once before the ratchet closes it forever. Every guarantee Crucible does make is machine-checked; everything it can't, it names.

10 — Dictionary

The words, decoded

Plain-dictionary meaning first, then what the word means inside Crucible.

Oracle noun

DictionaryIn software testing (a decades-old term of art): the mechanism that decides whether a test's output is correct.

In CrucibleA Given/When/Then scenario with a stable ID (ORC-lockout-001), bound to a real executable test. Drafted by the propose agent, sealed by the human at approve, immutable afterwards. The judges.

Spec delta noun

DictionaryDelta: the difference between two states.

In CrucibleThe change's new or modified promises — SHALL requirements with bracketed IDs ([REQ-auth-lockout-1]). On archive, deltas merge into specs/, the living contract. No delta → no new oracles needed (that's a refactor).

Binding noun

DictionarySomething that ties one thing to another.

In CrucibleThe fenced YAML block linking an oracle to its executable check: requirement ID, kind, runner, and an opaque target in the runner's native addressing. The seam between human-readable intent and machine execution.

Traceability lint noun

DictionaryLint: a static check that verifies structure without running anything.

In CrucibleThree extractions and set arithmetic, in milliseconds: every REQ has ≥1 oracle; every oracle points at a real REQ; every binding resolves to a test that actually exists. A requirement without an oracle fails the build — it's a wish.

Approval artifact noun

DictionaryA record that consent was given.

In Crucibleapproval.yaml: SHA-256 content hashes of every reviewed artifact and bound test, plus who and when. CI recomputes; any mismatch voids it. Tamper-evidence, not tamper-prevention — which turns out to be enough.

Amend verb

DictionaryTo make minor corrections to a formal document.

In CrucibleThe thirty-second re-seal: fix a scenario mid-implementation, the affected artifacts and tests regenerate, you confirm the diff, a delta entry with fresh hashes is appended. Also how escalations resolve. Fixing the spec upstream only survives if it's this cheap.

Escalation noun

DictionaryPassing a problem to someone with more authority.

In CrucibleWhat an agent must do on any decision the approved spec doesn't determine: file escalation.yaml with concrete options and stop. Implement cannot resume while one is unresolved. Ambiguity is a spec bug, fixed upstream — never improvised.

Override noun

DictionaryUsing special authority to bypass a rule.

In CrucibleThe honest 2 AM hatch: instant to use, impossible to use quietly. CI forces human review regardless of tier and auto-files a ratchet issue that stays open until a retroactive proposal lands. Visible bypass beats forbidden bypass.

Tier noun

DictionaryA level in a ranked series.

In Crucibletrivial · standard · critical — computed from the diff (spec delta? risk globs? size?), recomputed at every stage, forceable up but never down. Scales authoring ceremony and merge routing; never the executed safety net.

Risk glob noun

DictionaryGlob: a wildcard path pattern, like .gitignore uses.

In CrucibleThe declaration of where danger lives: src/**/payments/** → critical. A match dominates every other tier signal. The friendliest file in the repo, because it's the dial teams turn as trust calibrates.

Adapter noun

DictionaryA device that lets incompatible things work together.

In CrucibleA pinned, hash-locked executable speaking JSON over stdin/stdout, honoring resolve and run for one test runner. Part of the TCB — it decides whether checks pass — so it's certified by a conformance suite. Maps to runners, not frameworks.

Regression suite noun

DictionaryTests that catch reintroduced bugs.

In CrucibleThe union of every archived change's oracle bindings — nobody writes it; archiving is registration. The living, executable memory of every promise ever approved, and the entire correctness criterion for refactors.

Ratchet noun

DictionaryA mechanism that turns one way and locks against reversing.

In CrucibleThe dual rule: every escaped defect ships a gate commit (reproduction oracle, rubric line, or rule); every agent failure ships a harness commit. Enforced mechanically for bugfixes — the reproduction must be red on base, green on fix, or it can't merge.

Rubric noun

DictionaryThe scoring criteria a grader must apply.

In Crucible.crucible/rubric.yaml — the AI reviewer's law: versioned lines, each with an ID and the observable evidence that constitutes a finding. Ships with 12 defaults; grows into your institutional knowledge. The reviewer may not block on anything else.

Observations noun

DictionaryThings noticed, short of a formal charge.

In CrucibleThe reviewer's channel for concerns outside the rubric — attached to the PR, surfaced in the audit digest, promotable into rubric lines by humans. How the model's genuine insight is harvested without granting it an unbounded veto.

Seams noun

DictionaryWhere two pieces of material join — the classic weak point.

In CrucibleA required propose section listing the boundaries this change crosses: services touched, external contracts affected, shared schemas, concurrent in-flight changes. The riskiest unknowns, dragged into the reviewed bundle where a human sees them.

TCB initialism

DictionaryTrusted computing base: the minimal set of components that must be trusted for a system's guarantees to hold.

In CrucibleSpecs, oracles + bound tests, rubric, adapters, role prompts, CI workflows, enforcement config, the harness. Everything the implement agent cannot touch — which is precisely why the implement agent can be fully untrusted.

Target-branch rule noun

Dictionary—

In Crucible“The rules that judge you are the rules already on main.” CI reads enforcement config from the merge target, never the PR — so editing the rules inside a PR is inert, and team rule-tightening applies instantly to every open PR. Self-referential tamper-proofing with zero ceremony.

Trajectory noun

DictionaryThe path something takes, not just where it lands.

In CrucibleThe agent's captured session log, stored as an artifact. Output checks ask “is the result right?”; trajectory checks ask “was the path sound?” — did it actually run local verify, did it attempt to touch sealed paths. Captured today; judged progressively.

Mutation testing noun

DictionaryDeliberately injecting small bugs to see whether the tests notice.

In CrucibleThe test of the tests — the mechanical answer to vacuous oracles. Diff-scoped for speed; blocking on critical tier, async elsewhere (surviving mutants file ratchet issues instead of blocking merges).

11 — Roadmap

The gap between the north star and today

Design is complete and chartered. The build runs as a tracer bullet: one thin slice end-to-end first, then deepen.

North star: you describe intent in a chat, spend ten minutes at one gate, and production-grade software ships itself — with every promise it ever made still executable, forever.

Phase 0 — Spike & scaffold ★ next

Prove the OpenSpec custom-schema assumptions for real; pin the version range; scaffold the TypeScript monorepo, toy fixture, and stub adapter. Reconnaissance whose explicit job is to find where the charter is wrong.

Phase 1 — Tracer bullet ★ WIP

The thin slice: minimal propose → approve → implement → verify + status + one CI check, against a stub adapter. Ends at the permanent regression anchor: an integration test proving the happy path and the enforcement (post-approval oracle edit → red; skipped oracle → red; requirement without oracle → red).

Phase 2 — Deepen the loop

Tiers + routing, amend/override/escalate, change types with red-on-base/green-on-fix, the adversarial reviewer, the rich approve surface, init/doctor/why, notify hooks. Exit: all three worked examples above are executable, end to end.

Phase 3 — Real adapter: java-junit

Conformance fixtures first (they define “correct adapter” — the stub must pass them too), then the JUnit adapter: detect, run via JUnit XML, resolve via a small Launcher-API helper. Exit: a hello-world Spring Boot change flows end to end.

Phase 4 — Validation project

The success criterion, made falsifiable: a production-grade, consumer-ready Spring Boot product built entirely through Crucible — instrumented from day one (gate minutes, escalations, auto-merge rate, override count ≈ 0, escaped defects, verify latency). Evidence, not an anecdote.

Hardening — deliberately parked ★ later

Hermetic CI sandboxing (hashes + immutability carry tamper-evidence until then) · the reviewer's own regression eval suite (“set the bar at the eval, not the demo”) · deterministic trajectory checks · native non-test runners (SQL constraints, architecture rules) · canary/SLO signals auto-filing ratchet issues · org-scale platform hardening.

Today: none of these weaken the design — each has a named interim mechanism, and each is a listed backlog item, not a forgotten wish.

Crucible — approve the promise, never read the code.
Agents draft the judges and the work; a human seals the judges; machines guarantee the rest.
